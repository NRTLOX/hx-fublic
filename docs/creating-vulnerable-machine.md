# Как создать уязвимую машину для задания (Proxmox VM)

Гайд для админов площадки: полный цикл от пустой VM в Proxmox до рабочего
задания типа «Виртуальная машина» на сайте. Общий процесс одинаков для
любой уязвимости — меняется только шаг 5 (сама уязвимость).

## 0. Перед началом

- Доступ к Proxmox: `https://<PROXMOX_HOST>:8006` (тот же хост, что в
  `PROXMOX_HOST` в `.env`), нода — значение `PROXMOX_NODE`.
- **ID шаблона резервируем из диапазона `900–989`.** Причина: ID для
  реальных клонов машин площадка генерирует по формуле
  `8{user_id}00{task_id}` (`vms/views.py:generate_vm_id`) — это всегда
  число от 5 цифр и начинается с `8` (например `81001`, `8712500`). Любой
  ID в диапазоне 900–989 никогда не пересечётся с этой схемой.
- Заранее реши, что именно будет уязвимостью и на каком порту/сервисе —
  дальше по шагам.

## 1. Создать VM в веб-интерфейсе Proxmox

`Create VM` на нужной ноде:

- **General** — VM ID: `9xx` из зарезервированного диапазона, Name:
  осмысленное имя-шаблон, например `tpl-easy-sqli`.
- **OS** — прикрепи ISO для установки (рекомендуется Debian 12 netinstall
  или Ubuntu Server minimal — меньше диска, быстрее клонирование).
- **System** — обязательно отметь галку **Qemu Agent** (можно и позже
  включить командой, см. шаг 3).
- **Disks** — virtio, 8–16 GB достаточно для минимальной ОС + сервис.
- **CPU/Memory** — по минимуму (1 vCPU, 1024–2048 MB) — машины
  запускаются параллельно у разных студентов.
- **Network** — bridge, на котором висит лабораторная сеть (`vmbr0` или
  как настроено на ноде), модель адаптера VirtIO.

Запусти VM и поставь ОС обычным образом (минимальная установка, без GUI,
SSH-сервер — по желанию).

## 2. Установить и настроить ОС

Ничего специфичного — минимальная установка, обновления:

```bash
apt update && apt upgrade -y
```

## 3. QEMU Guest Agent

Без агента площадка не сможет ни вставить флаг, ни проверить готовность
машины — `proxmox_client.exec_command()` работает именно через
`qm guest exec`, который требует запущенный agent внутри гостя.

Внутри VM:

```bash
apt install -y qemu-guest-agent
systemctl enable --now qemu-guest-agent
```

На стороне Proxmox (если не отметил галку на шаге 1):

```bash
qm set <VMID> --agent enabled=1
```

## 4. Сеть: Cloud-Init (обязательно для авто-IP)

Площадка назначает IP клону не вручную, а через
`proxmox_client.set_ip()` → `qm ... config.put(ipconfig0=...)`. Это
Proxmox Cloud-Init параметр — он реально применится внутри гостя только
если у VM есть Cloud-Init диск и внутри установлен `cloud-init`.

**Важен порядок.** Сначала подключи Cloud-Init диск на стороне Proxmox
(подставь имя своего storage, например `local-lvm`):

```bash
qm set <VMID> --ide2 local-lvm:cloudinit
qm set <VMID> --boot order='scsi0;ide2'
```

И только потом ставь пакет внутри VM:

```bash
apt install -y cloud-init
```

Если сделать наоборот (сначала `apt install cloud-init`, потом
прицепить диск) — при установке пакета сработает `ds-identify`, не
найдёт валидный датасорс (CD-ROM с cloud-init ещё не подключён),
решит, что машина не облачная, и создаст
`/etc/cloud/cloud-init.disabled`, замаскировав все cloud-init unit'ы.
После этого cloud-init выключен навсегда — конфиг с IP по-прежнему
будет исправно генерироваться Proxmox'ом (`qm cloudinit dump <VMID>
network` покажет корректный static-конфиг), но гость его никогда не
прочитает, и `ip a` внутри так и останется без нужного адреса.

Если это уже произошло — почини на самом шаблоне, иначе баг унаследует
каждый новый клон:

```bash
qm guest exec <VMID> -- bash -c "
rm -f /etc/cloud/cloud-init.disabled
mkdir -p /etc/cloud/cloud.cfg.d
echo 'datasource_list: [ NoCloud, ConfigDrive ]' > /etc/cloud/cloud.cfg.d/99_pve.cfg
systemctl unmask cloud-init-local.service cloud-init.service cloud-config.service cloud-final.service cloud-init-network.service
systemctl enable cloud-init
cloud-init clean --logs
reboot
"
```

Проверка после ребута:

```bash
qm guest exec <VMID> -- cloud-init status --long
qm guest exec <VMID> -- ip -4 a
```

> Примечание: шлюз при вызове `set_ip()` сейчас захардкожен в коде как
> `10.100.50.1` независимо от подсети пользователя — это ограничение
> платформы, а не шаблона; на этот шаг никак не влияет, просто держи в
> голове, если после клонирования IP есть, а маршрутизации нет.

Проверить после первого клона/старта: `ip a` внутри гостя должен
показать выданный `set_ip()` адрес.

## 5. Сделать машину уязвимой

Тут — сама суть задания. Общий чек-лист вне зависимости от конкретной
уязвимости:

1. Разверни сервис/сайт с нужной уязвимостью. Два типовых варианта:
   - **Нативно**: `apt install <пакет>`, осознанно ослабь конфиг (дефолтные
     креды, отключённая аутентификация, неправильные права на файлы,
     устаревшая уязвимая версия пакета), включи автозапуск:
     ```bash
     systemctl enable --now <service>
     ```
   - **Docker**: удобно для готовых уязвимых образов (DVWA, vulhub и т.п.).
     Обязательно `--restart unless-stopped`, иначе после ребута гостя
     (который платформа делает при каждом старте VM) сервис не поднимется:
     ```bash
     apt install -y docker.io
     docker run -d --name vuln-web --restart unless-stopped -p 80:80 \
       vulnerables/web-dvwa
     ```
2. Слушай на `0.0.0.0`, а не `127.0.0.1` — иначе сервис недоступен снаружи
   VM. Проверь:
   ```bash
   ss -tlnp
   ```
3. Убедись, что локальный firewall внутри гостя (если есть — `ufw`,
   `nftables`) не режет нужный порт, либо явно его открой.

## 6. Подготовить путь под флаг

Площадка вставляет флаг командой вида `echo '<флаг>' > <file_path>`
через guest agent (от root), а `file_path` — то самое поле, которое
позже укажешь в админке у объекта `Flag`.

- Заранее реши и создай путь, например `/var/www/html/flag.txt` (для
  веб-доступного флага) или `/root/flag.txt` (если флаг должен требовать
  привилегированный доступ — тогда сервис-эксплойт должен приводить к
  чтению файлов от root).
- Убедись, что сервис, который должен «раздать» флаг после эксплуатации
  уязвимости, реально сможет его прочитать (права на файл/директорию).
- Можно проверить вставку вручную ещё до регистрации задания на сайте,
  той же командой, что использует платформа:
  ```bash
  ssh root@<PROXMOX_HOST> "qm guest exec <VMID> -- bash -c \"echo 'test' > /var/www/html/flag.txt\""
  ```

## 7. Почистить и превратить VM в шаблон

Перед превращением в шаблон — типовая гигиена образа, чтобы клоны не
шарили machine-id/SSH host keys:

```bash
apt clean
rm -f /etc/machine-id && systemd-machine-id-setup
cloud-init clean --logs
shutdown -h now
```

Когда VM выключена, на стороне Proxmox:

```bash
qm template <VMID>
```

Важно: `clone_vm()` в коде площадки использует полный клон (`full=1`),
поэтому после `qm template` можно спокойно штамповать клоны — они не
зависят от состояния диска шаблона после клонирования.

## 8. Зарегистрировать задание в Django-админке

`/admin/tasks/task/add/`:

- **Тип задания** — «Виртуальная машина».
- **ID шаблона в Proxmox** — тот же `<VMID>`, что заshаблонили на шаге 7.
- Заполни название, описание, баллы, README (файл).
- Добавь один или несколько объектов **Flag**:
  - `file_path` — точно тот путь, что подготовил на шаге 6;
  - `flag_value` — оставь пустым, площадка генерирует уникальный флаг на
    каждого студента автоматически;
  - `label`/`hint`/`description` — по желанию.
- `is_active` — включи, когда протестируешь (см. шаг 9).

## 9. Сквозной тест

1. Зайди на сайт под тестовым пользователем, открой задание, нажми
   «Запустить машину».
2. В серверных логах — строки `[VM][DEBUG]`, `[Proxmox]`, `[VM]`
   покажут клонирование → назначение IP → старт → ожидание agent'а →
   вставку флага.
3. Подключись по VPN, проверь доступность выданного IP на нужном порту.
4. Пройди уязвимость сам, убедись, что флаг реально читается через
   эксплуатацию, а не только лежит на диске.

## Частые грабли

- **Agent не запущен в шаблоне** → `exec_command` фейлится, вставка
  флага и проверка готовности отваливаются по таймауту (120 сек) —
  `start_vm` упадёт с исключением.
- **Нет Cloud-Init диска** → `set_ip()` отработает без ошибки на стороне
  Proxmox API, но IP внутри гостя не появится.
- **Cloud-init сам себя выключил** (`apt install cloud-init` был
  раньше, чем `qm set --ide2 ...cloudinit`) → `qm cloudinit dump <VMID>
  network` показывает корректный конфиг, а `qm guest exec <VMID> --
  cloud-init status --long` внутри гостя выдаёт `Cloud-init disabled by
  /etc/cloud/cloud-init.disabled`. См. фикс в шаге 4.
- **Сервис слушает только `127.0.0.1`** — самая частая причина «машина
  вроде создалась, а зайти не могу».
- **Docker-контейнер без `--restart unless-stopped`** — после
  остановки/повторного старта VM платформой уязвимый сервис не поднимется
  сам.
- **ID шаблона вне диапазона 900–989** — теоретический риск пересечения
  с ID реального клона; проще не рисковать и держаться зарезервированного
  диапазона.
